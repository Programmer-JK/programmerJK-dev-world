위키에서 추출한 HTML을 Oracle로 옮기는 도구를 Eclipse 실행용 클래스에서 시작해 웹 화면까지 만들었다.

## 흐름

1. **조각 적재** — 본문 `main-content` div만 읽어 태그 경계로 조각내고, 이미지는 base64로 바꿔 임시 테이블에 저장
2. **한 건으로 합치기** — 기록 1건마다 [프로시저](/posts/oracle-temporary-lob-space)를 호출해 CLOB으로 적재
3. **웹 실행** — 백그라운드에서 하나씩 처리, 화면이 진행률·로그를 폴링
4. **검증** — DB의 base64를 다시 풀어 원본 파일과 SHA-256 대조

## 정규식 — 이어 붙이면 원문과 같게

```java
static final int BATCH = 500;
static final int BIG = 1000;     // 이보다 긴 조각은 배치 대신 스트림 단건 insert
static final int CHUNK = 1000;   // 이미지가 아닌 조각의 최대 길이

// <div ... id="main-content" ...>
static final Pattern START = Pattern.compile(
    "<div\\b[^>]*\\bid\\s*=\\s*([\"'])main-content\\1[^>]*>",
    Pattern.CASE_INSENSITIVE);
static final Pattern DIV = Pattern.compile("<(/?)div\\b", Pattern.CASE_INSENSITIVE);

// 태그 하나 | 짝 없는 '<' | 태그 사이의 글자들
static final Pattern TOKEN = Pattern.compile("<[^>]*>|<|[^<]+");
static final Pattern IMG_TAG = Pattern.compile("^<img\\b", Pattern.CASE_INSENSITIVE);
```

- `Pattern.compile`은 비용이 커서 `static final`로 한 번만 만든다.
- `([\"'])…\\1`은 역참조 — 여는 따옴표와 같은 종류로 닫혀야 매칭된다.
- `DIV`로 깊이를 세어 main-content 영역이 끝나는 지점을 찾는다.
- **`TOKEN`의 세 경우가 모든 글자를 덮는다.** 그래서 `find()` 결과를 이어 붙이면 원문 그대로다. 이 규칙을 먼저 정하니 분할과 복원이 단순해졌다.
- 이미지 태그는 다른 조각과 섞지 않고 단독 행으로 둔다.

## 큰 조각은 스트림으로

```java
for (String chunk : chunks) {
  final int lineNo = ++no;
  String c = HtmlImg.embed(chunk, (src, e) -> {
    imgFail++;
    writeLog(log, name + ":" + lineNo, src + "\t" + e);
  });
  ins.setString(1, name);
  ins.setInt(2, lineNo);
  if (c.length() > BIG) {
    if (pending > 0) { ins.executeBatch(); pending = 0; }   // 순서 유지
    ins.setCharacterStream(3, new StringReader(c), c.length());
    ins.executeUpdate();
  } else {
    ins.setString(3, c);
    ins.addBatch();
    if (++pending == BATCH) { ins.executeBatch(); pending = 0; }
  }
}
```

- `addBatch`/`executeBatch`는 왕복을 줄이지만 모은 만큼 메모리를 차지한다.
- 큰 CLOB을 `setString`으로 넣으면 드라이버가 전체 문자열을 메모리에 들고 처리하고 크기 제한에도 걸린다. `setCharacterStream`으로 흘려보낸다.
- 배치와 단건을 섞을 때는 단건 전에 쌓인 배치를 먼저 비워 순서를 지킨다.
- 람다는 사실상 final인 지역 변수만 캡처할 수 있어서 `final int lineNo = ++no`로 따로 받았다.

## 이미지를 data URI로, 큰 사진은 축소

```java
static final long MAX_BYTES = 20L * 1024 * 1024;   // 이보다 큰 원본은 변환하지 않음
static final int MAX_SIDE = 1280;                    // 긴 변 기준
static final int RECOMPRESS_BYTES = 300 * 1024;      // 작아도 이보다 크면 재압축
static final float JPEG_QUALITY = 0.8f;

// \ssrc: data-image-src 제외, (?!data:): 이미 변환된 것 제외
static final Pattern IMG = Pattern.compile(
    "(<img\\b[^>]*?\\ssrc\\s*=\\s*)([\"'])(?!data:)([^\"']*attach[^\"']*)\\2",
    Pattern.CASE_INSENSITIVE);

static String embed(String line, ErrorLog err) throws IOException {
  Matcher m = IMG.matcher(line);
  StringBuilder sb = null;
  int last = 0;
  while (m.find()) {
    String uri;
    try {
      uri = toDataUri(m.group(3));
    } catch (IOException | RuntimeException e) {
      err.write(m.group(3), e);      // 이 이미지만 건너뜀
      continue;
    }
    if (sb == null) sb = new StringBuilder(line.length() + uri.length());
    sb.append(line, last, m.start(3)).append(uri);
    last = m.end(3);
  }
  if (sb == null) return line;       // 이미지 없는 조각은 복사 비용 없음
  return sb.append(line, last, line.length()).toString();
}
```

- `(?!data:)`는 부정 전방 탐색 — 글자를 소비하지 않고 "뒤가 data:가 아님"만 확인한다.
- `\\ssrc`로 앞 공백을 요구해 `data-image-src` 같은 속성을 제외한다.
- 이미지 하나가 실패해도 `continue` — 원래 경로가 그대로 남아 나중에 확인할 수 있다.

### 왜 축소했나

base64는 약 33% 커지고, Java 8 문자열은 글자당 2바이트(UTF-16)라 메모리에서는 원본의 약 **2.7배**다. StringBuilder·정규식 결과 같은 복사본까지 생각하면 몇 배 더 필요하다. 원본 사진을 그대로 넣다가 [WAS가 OOM으로 죽었다](/posts/orgn-migration-postmortem).

- `ImageIO.read` → `BufferedImage`, 새 캔버스에 `Graphics2D.drawImage`로 줄여 그린다.
- JPEG 품질은 `ImageWriteParam.setCompressionQuality(0.8f)`.
- 휴대폰 사진은 픽셀은 그대로 두고 **EXIF Orientation 태그로 회전을 표시**한다. 다시 저장하면 태그가 사라지므로 회전을 먼저 픽셀에 반영한다.
- ImageIO가 못 읽는 형식(CMYK JPEG 등)은 원본을 유지한다.

## 검증과 진행률 폴링

```java
// base64를 풀어 원본과 SHA-256 대조
byte[] bytes = Base64.getDecoder().decode(b64);
Path same = originals.get(sha(bytes));
```

축소·재압축한 이미지는 해시가 달라지므로 원본 그대로 넣은 이미지에만 의미 있는 검사다.

```javascript
try {
  render(s);
} catch (e) {
  if (window.console) console.error('render 오류', e, s);
}
if (s.state === 'RUNNING') schedule();   // DONE / FAILED 에서는 저절로 멈춤
```

`setInterval`은 응답과 상관없이 요청해서 응답이 늦으면 요청이 쌓이고, 해제를 잊으면 멈추지 않는다. **응답을 받은 뒤 `setTimeout`으로 다음 한 번만 예약**하면 요청이 겹치지 않고, 종료 상태에서 예약하지 않는 것만으로 멈춘다.

## 웹 실행 화면

- 서버 폴더 경로 입력 → 백그라운드 스레드에서 실행
- 허용된 루트 밖 경로는 차단, 동시에 하나만 실행
- 중지하면 처리 중인 파일은 롤백, 이미지 변환에 실패한 파일은 보류
- 파일 단위로 커밋·롤백해서 재실행이 쉽다

## 클래스 초기화 함정

- static 필드 초기화 중 예외 → 첫 사용 시 `ExceptionInInitializerError`, 이후에는 `NoClassDefFoundError`. 클래스가 초기화 실패 상태로 남아 **재시작 전까지 계속 깨진다.** 외부 설정(JNDI 이름 등)은 실행 시점에 읽도록 옮겼다.
- 익명·내부 클래스는 `바깥$1.class`처럼 별도 파일로 컴파일된다. 이게 [배포에서 문제](/posts/closed-network-deploy-lessons)가 됐다.

## 배운 것

- "이어 붙이면 원문과 같다"는 규칙을 먼저 정하면 분할과 복원이 단순해진다.
- 데이터 단위는 원천 파일이 아니라 **조회 단위**(기록 1건)에 맞춘다.
- 이미지는 화면에 보일 크기로 저장하고, 다시 저장할 땐 EXIF 회전부터 반영한다.
