업로드, 삭제 차단, 마감처럼 상태를 바꾸는 작업을 프로시저로 만들었다. 공통 질문은 "실패하면 어디까지 되돌리나"와 "동시에 누르면 어떻게 되나"였다.

## PL/SQL 예외 처리 기본

- **미리 정의된 예외**: `NO_DATA_FOUND`(SELECT INTO 0행), `TOO_MANY_ROWS`(2행 이상), `DUP_VAL_ON_INDEX`(유니크 위반)
- **사용자 정의 예외**: `E_X EXCEPTION;` 선언 후 `RAISE E_X;`
- `RAISE_APPLICATION_ERROR(-20000 ~ -20999, 메시지)`: 호출자에게 ORA 오류로 전달한다. 하지만 **같은 블록의 `WHEN OTHERS`가 잡으면 밖으로 안 나간다.**
- `WHEN OTHERS`: 나머지 전부. 잡고 `RAISE` 없이 끝내면 오류가 사라진다.
- 핸들러는 위에서부터 처음 맞는 하나만 실행된다.

## 엑셀 업로드 프로시저

순서: 대상 확인 → 파일 내 중복 → 기등록 중복 → INSERT → 임시 테이블 삭제. 실패하면 SAVEPOINT까지 롤백한다.

```sql
SAVEPOINT SP_UPLOAD_START;
...
EXCEPTION
  WHEN E_UPLOAD_ERROR THEN
    ROLLBACK TO SP_UPLOAD_START;
    O_RSLT_CD := 'E';  O_INS_CNT := 0;
  WHEN TOO_MANY_ROWS THEN
    ROLLBACK TO SP_UPLOAD_START;
    O_RSLT_CD  := 'E';
    O_RSLT_MSG := '행번 또는 조직코드가 중복 조회되었습니다.';
    O_INS_CNT  := 0;
  WHEN DUP_VAL_ON_INDEX THEN
    ROLLBACK TO SP_UPLOAD_START;
    O_RSLT_CD  := 'E';
    O_RSLT_MSG := '중복된 데이터가 존재하여 등록에 실패했습니다.';
    O_INS_CNT  := 0;
  WHEN OTHERS THEN
    ROLLBACK TO SP_UPLOAD_START;
    O_RSLT_CD  := 'E';
    O_RSLT_MSG := '업로드 처리 중 오류가 발생했습니다. ' || SQLERRM;
    O_INS_CNT  := 0;
END;
```

- **SAVEPOINT**는 트랜잭션 중간의 표시점이다. `ROLLBACK TO`는 그 뒤 작업만 취소하고 트랜잭션은 계속되므로 호출자의 앞선 작업은 살아 있다.
- `TOO_MANY_ROWS`는 원본 데이터 중복, `DUP_VAL_ON_INDEX`는 사전 검사를 통과했는데도 생긴 위반(동시 업로드 등)이다.
- 예외를 다시 던지지 않고 **OUT 파라미터**(결과 코드·메시지·건수)로 돌려준다. 화면은 결과 코드로 분기한다.

처음엔 서브쿼리마다 키 변환을 반복해 행이 중복됐다. 키 변환을 `WITH` 맨 위에서 한 번만 하고 `LEFT OUTER JOIN`으로 내려보내 해결했다.

### 동시 업로드 격리 — GTT 검토

```sql
CREATE GLOBAL TEMPORARY TABLE UPLOAD_TEMP (
  ORG_CD VARCHAR2(20), EMP_NO VARCHAR2(20), ETC01 VARCHAR2(1000)
) ON COMMIT DELETE ROWS;
```

GTT는 정의는 공유하고 데이터는 세션마다 따로 보인다. 두 사용자가 동시에 올려도 임시 데이터가 섞이지 않는다. 다만 `ON COMMIT DELETE ROWS`는 중간에 커밋하면 그 순간 비워지고, `PRESERVE ROWS`는 커넥션 풀이 세션을 재사용하므로 직접 지워야 한다.

## 삭제 차단 — WHEN OTHERS가 오류를 삼켰다

하위 평가대상이 있으면 삭제를 막으려고 `RAISE_APPLICATION_ERROR`를 넣었는데, 기존 프로시저의 `WHEN OTHERS`가 그 오류를 삼켜 버렸다.

**해결**: OUT 파라미터에 메시지를 넣고 조기 `RETURN`. 기존 구조에 `WHEN OTHERS`가 있으면 사용자 오류는 OUT 파라미터로 돌려주는 편이 안전하다.

## 마감 — 하나를 Y로 바꾸면 나머지는 N

> 프로시저 자체는 동시성을 보장하지 않는다. 막아주는 건 **행 잠금**이다.

```sql
CREATE OR REPLACE PROCEDURE set_close_flag (
  p_group_id IN my_table.group_id%TYPE,
  p_id       IN my_table.id%TYPE
) AS
  v_dummy NUMBER;
BEGIN
  SELECT 1 INTO v_dummy FROM close_group       -- 1) 그룹 단위 직렬화
   WHERE group_id = p_group_id
     FOR UPDATE WAIT 5;

  UPDATE my_table                              -- 2) 대상은 Y, 나머지는 N
     SET flag = CASE WHEN id = p_id THEN 'Y' ELSE 'N' END
   WHERE group_id = p_group_id
     AND flag <> CASE WHEN id = p_id THEN 'Y' ELSE 'N' END;

  SELECT 1 INTO v_dummy FROM my_table          -- 3) 대상 존재 확인
   WHERE group_id = p_group_id AND id = p_id;
EXCEPTION
  WHEN NO_DATA_FOUND THEN
    ROLLBACK;
    RAISE_APPLICATION_ERROR(-20001, '그룹 또는 대상 행이 없습니다.');
END;
/
CREATE UNIQUE INDEX ux_my_table_one_y
  ON my_table (CASE WHEN flag = 'Y' THEN group_id END);   -- N은 NULL → 인덱스 제외
```

- 그룹 마스터 행을 먼저 잠근다. 같은 그룹 요청은 여기서 줄을 서고 다른 그룹은 영향이 없다. 항상 같은 "대표 행"부터 잡으니 **데드락 순서도 고정**된다.
- UPDATE 한 문장에서 대상은 Y, 나머지는 N. 이미 값이 맞는 행은 건드리지 않는다.
- 대상 행이 없어도 UPDATE는 오류 없이 0건이다. `SQL%ROWCOUNT`는 "이미 Y라서 0건"과 구분이 안 되므로 `SELECT INTO`로 확인한다.
- **함수 기반 유니크 인덱스**: B-tree는 키가 전부 NULL인 행을 저장하지 않는다. Y일 때만 값이 생기므로 "그룹당 Y 하나"만 검사 대상이 된다. 잠금을 거치지 않는 다른 경로까지 막는 마지막 방어선이다.
- **토글보다 목표값**: 두 번 누르면 토글은 원상복구된다. 목표 상태를 명시해야 중복 요청에 안전하다.

실제로는 마감과 마감 해제 두 프로시저로 나눠 구현했다.

## 행 잠금 요약

- `UPDATE`·`DELETE`·`SELECT … FOR UPDATE`는 대상 행을 커밋·롤백까지 잠근다.
- 단순 조회는 잠금에 막히지 않는다(일관 읽기).
- `WAIT n` / `NOWAIT`을 넘기면 `ORA-30006` / `ORA-00054`.
- 두 세션이 서로 다른 순서로 행을 잡으면 `ORA-00060` 데드락.

## 자주 본 오류

- `ORA-17003` 부적합한 열 인덱스 — JDBC 쪽 `?` 개수·번호 불일치. MyBatis라면 `statementType="CALLABLE"`과 `mode=OUT` 누락이 흔하다.
- `ORA-06502` 변수 크기 부족 — `%TYPE`을 쓰고, 한글은 `VARCHAR2(n CHAR)`.
