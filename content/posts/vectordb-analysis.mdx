## Vector란?

데이터의 묶음은 여러의미의 데이터들로 이루어진 경우가 많은데, 이를 **특정한 순서대로 모아둔 데이터 레코드**를 선형대수에서는 **Vector**라고 부릅니다. 그리고 **행렬(Matrix)** 은 이러한 **벡터가 여러개 있는 데이터의 집합**이라고 생각하면 될 것 같습니다.

## VectorDB는 무엇인가?

VectorDB는 벡터 형식의 데이터를 저장하고 쿼리 분석하는데 특화된 데이터베이스입니다. 수학적으로 벡터는 공간상의 점, 또는 다차원 공간에서의 위치를 말합니다. VectorDB는 이런 위치 정보를 저장, 관리, 사용하는데 초점을 둔 Database입니다. 기본적으로 테이블 구조를 가지고 key를 기반으로 데이터를 얻는 관계형데이터베이스에 반해, VectorDB는 전체 데이터들과 쿼리간의 유사도를 계산하고, 가장 유사도가 높은 데이터를 추출해야 한다는 목적성을 가지고 있습니다.

## Embedding이란?

 기본적으로 plain text는 인간이 알아보기는 쉽지만 컴퓨터가 이해하기 쉬운 표현은 아닙니다. 그래서 텍스트나 이미지 같은 비정형 데이터를 기계가 잘 이해할 수 있게 고차원의 벡터 형태로 변환해주는 작업이 필요합니다.

### One-Hot Encoding

예전에는 **One-Hot Encoding**이라는 기법을 통해 단어를 숫자벡터로 변환했었습니다.

예를 들어 `I like rabbit and I hate coriander` 라는 문장을 벡터화한다면 먼저 단어단위로 분해하고
(`I`, `like`, `rabbit`, `and`, `I`, `hate`, `coriander`)  그 다음, 
`{ 'I': 1, 'like': 2, 'rabbit': 3, 'hate': 4, 'coriander': 5 }`으로 정수를 부여하게 됩니다.  
이 과정을 정수 인코딩(Integer Encoding)이라고 합니다.

> **정수 인코딩(Integer Encoding)**  
> 단어를 빈도수 순으로 정렬한 단어집합(vocabulary)을 만들고 빈도수가 높은 순서대로 낮은 숫자부터 정수를 부여

이렇게 정수를 부여하고 나서, 이를 one-hot vector로 나타내면 아래와 같이 표현할 수 있습니다.

`I` : [1,0,0,0,0]  
`like` : [0,1,0,0,0]  
`rabbit` : [0,0,1,0,0]  
`hate` : [0,0,0,1,0]  
`coriander` : [0,0,0,0,1]

이런식으로 간단하게 벡터화를 할 수 있지만, 단어의 개수가 늘어날수록 벡터를 저장하기 위한 공간이 계속 늘어나게 됩니다.  
예를 들어 단어가 10000개라면, 각각의 단어는 10000개의 차원을 가진 벡터가 되겠죠!  
**공간의 활용에 있어서 비효율적**이라는 단점이 있습니다.

그리고 이렇게 표현하게 되면 단어의 존재는 쉽게 확인할 수 있지만, 각 **단어간 관계성을 파악하기 힘들다**는 단점도 존재합니다.  
특히 단어간 유사도가 중요한 검색시스템같은 환경에서는 큰 문제가 될 것입니다.  
(ex. one-hot vector에서 book과 books는 서로 다른 단어로 취급)

### Word Embedding

그래서 이를 보완하기 위해 **단어의 의미**를 다차원 공간에 벡터화하는 방법을 사용하기 시작합니다.

이와 같이 단어간 의미적 유사성을 벡터화 하는 작업을 **워드 임베딩(Word Embedding)** 이라 부르고, 이렇게 표현된 벡터를 **임베딩 벡터(Embedding Vector)** 라고 부릅니다.

**비슷한 문맥에서 등장하는 단어들은 비슷한 의미를 가질 것이다~** 라는 가설(Distributional Hypothesis)를 전제로, 비슷한 내용의 단어들을 벡터화 시키면 그 벡터들은 유사한 벡터값을 가지게 됩니다.

이렇게 하면 **단어의 의미를 여러 차원에다 분산하여 표현할 수 있고, 단어벡터간 유의미한 유사도를 계산할 수 있게 됩니다.**

> 아래 예시에서 `고양이`와 `개`는 의미론적 관계를 반영해 서로 가깝지만 `행복`과 `슬픔`은 반대방향이므로 대조되는 의미임을 알 수 있습니다.
> 
> ```
> 고양이 [0.2, -0.4, 0.7]
> 개 [0.6, 0.1, 0.5]
> 사과 [0.8, -0.2, -0.3]
> 오렌지 [0.7, -0.1, -0.6]
> 행복 [-0.5, 0.9, 0.2]
> 슬픔 [0.4, -0.7, -0.5]
> ```

embedding vector를 만드는데 최적화된 모델인 **embedding model**을 사용하여 벡터화하게됩니다.

![](https://raw.githubusercontent.com/GRuuuuu/hololy-img-repo/main/2024/2024-05-02-vector-store.md/1.png)

사람이 embedding vector를 확인하고 의미를 파악하기는 어려우나, 서로 다른 단어나 문서로부터 추출된 **embedding vector들간의 거리를 계산하면 이들간의 의미적 관계를 파악**할 수 있습니다.

또한 embedding model을 어떤걸 사용하느냐에 다라 embedding vector의 값과 차원이 다르게 표현됩니다.  
따라서 usecase에 맞게 embedding model을 선택하는 것도 중요합니다.

## Embedding 모델 선택

HR 시스템에 적합한 임베딩 모델을 선택하기 위해 5개의 후보 모델을 대상으로 종합적인 비교 평가를 수행했습니다.

### 비교 대상 모델

평가 대상 모델은 다음과 같습니다:

1. **intfloat/multilingual-e5-large** (1순위)
2. **intfloat/multilingual-e5-large-instruct** (2순위)
3. **BAAI/bge-m3** (3순위)
4. **Alibaba-NLP/gte-multilingual-base**
5. **mixedbread-ai/mxbai-embed-large-v1**

### 기본 스펙 비교

|항목|multilingual-e5-large|multilingual-e5-large-instruct|bge-m3|gte-multilingual-base|mxbai-embed-large-v1|
|---|---|---|---|---|---|
|**임베딩 차원수**|1024|1024|1024|768|1024|
|**다운로드 수**|2,280,416|1,341,848|7,035,741|1,425,729|2,674,637|
|**좋아요 수**|1,070|574|2,450|327|735|
|**파라미터 수**|559M|559M|560M|~280M|~340M|
|**메모리 크기**|1.04GB|1.1GB|1.06GB|~1.1GB|~1.3GB|
|**STSBenchmark**|0.854778|0.856864|0.848468|0.864555|0.892896|

**스펙 분석:**

- **임베딩 차원수**: 높은 차원일수록 많은 정보를 담을 수 있어 정확도가 올라가지만, 할루시네이션이 발생할 가능성도 높아집니다.
- **다운로드 수**: bge-m3가 가장 높지만, 중국에서 만든 모델인 만큼 중국인 사용자 비중이 클 가능성이 있습니다. intfloat 모델들은 다운로드 수 대비 좋아요 비율이 높아 실제 사용자 만족도가 높은 것으로 판단됩니다.
- **파라미터 수**: 클수록 커스터마이징 자유도가 크지만, 현재 PoC 상황에서는 큰 의미가 없습니다.
- **메모리 크기**: 모든 모델이 1~1.3GB 범위로 판단에 영향을 줄 정도의 용량 차이는 없습니다.
- **STSBenchmark**: 모든 모델이 0.84 이상의 높은 점수를 기록했으며, 이는 의미적 유사도 판단 기본 성능이 우수함을 의미합니다.

### 실제 테스트 결과 분석

HR 도메인 특화 데이터를 활용한 7개의 실제 테스트를 수행했습니다.

#### 테스트 1: 인사평가 제도 설명 검색

**쿼리**: "인사평가 제도를 설명해줘"

**결과 분석**:

- **multilingual-e5-large**: 1순위 유사도 0.88251로 "인사평가" 내용을 정확히 검색
- **multilingual-e5-large-instruct**: 1순위 유사도 0.90643로 가장 높았으나 실제로는 "인사제도"를 1순위로 반환
- **bge-m3**: 유사도는 낮지만(0.69623) 정확한 답을 찾음

**인사이트**: 유사도 점수가 높다고 해서 항상 더 정확한 결과를 반환하는 것은 아닙니다. 이는 모델 내부의 벡터화 로직 차이로 추정되며, 파인튜닝 시 성능 체크가 필수적입니다.

#### 테스트 2: 직원 기본 정보 테이블 구조 검색

**쿼리**: "직원의 기본 정보를 저장하는 테이블 구조"

**결과 분석**:

- **multilingual-e5-large**: employees 테이블을 1순위(0.87920)로 정확히 검색
- **multilingual-e5-large-instruct**: 더 높은 유사도(0.94858)로 동일하게 정확한 결과 반환
- **bge-m3**: 상대적으로 낮은 유사도(0.74543)

**인사이트**: multilingual-e5-large 계열 모델은 1순위와 2순위의 유사도 차이가 적은 반면, 다른 모델들은 차이가 큽니다. 이는 향후 유사도 판단 시 더 명확한 답변이 가능하다는 긍정적 신호입니다.

#### 테스트 3: 단일 키워드 검색 (연봉)

**쿼리**: "연봉"

**결과 분석**:

- **multilingual-e5-large & -instruct**: 모두 동일하게 "연봉" 용어 사전 + 테이블 컬럼명을 정확히 검색
- **bge-m3**: 테이블 정보 위주로 검색
- **mxbai-embed-large-v1**: 언어 사전의 문장 위주로 검색

**인사이트**: 모델마다 검색 우선순위가 다르며, multilingual-e5 계열이 가장 균형잡힌 결과를 제공합니다.

#### 테스트 4: 유사 용어 검색 (근무 시간)

**쿼리**: "근무 시간"

**결과 분석**:

- **multilingual-e5-large-instruct**: 1순위로 "근로시간" 용어를 정확히 찾음 (0.91368)
- **bge-m3**: "근무"보다는 "시간" 키워드 위주로 검색하여 관련성이 낮은 결과 반환

**인사이트**: multilingual-e5-large-instruct가 언어 사전과 테이블 정보를 균형있게 검색하여 우수한 성능을 보였습니다.

#### 테스트 5-6: 다중 키워드 검색

**테스트 5 쿼리**: "연봉 보너스 급여 관리" **테스트 6 쿼리**: "근무 시간 출퇴근 기록 휴가 신청"

**결과 분석**:

- multilingual-e5-large와 -instruct 모두 다중 키워드를 종합적으로 이해하여 관련 테이블과 용어를 정확히 검색
- 테스트 5에서는 동일한 결과, 테스트 6에서는 서로 다른 우선순위를 보임
    - **-instruct**: 근태 관련 내용 우선
    - **-large**: 휴가 관련 내용 우선
- **mxbai-embed-large-v1**: 별개의 관련 없는 정보 반환

#### 테스트 7: 전문 용어 검색 (HRIS)

**쿼리**: "HRIS 조직도 부서 직급"

**결과 분석**:

- **multilingual-e5-large**: HRIS 용어 사전을 1순위로 정확히 검색 (0.87835)
- **mxbai-embed-large-v1**: 내용이 변환되어 나타나는 이슈 발생

**인사이트**: 전문 용어 검색에서 multilingual-e5-large가 가장 안정적인 성능을 보였습니다.

### 종합 평가 및 최종 선택

#### 모델별 강점 분석

**1순위: intfloat/multilingual-e5-large**

- ✅ 단일 키워드와 다중 키워드 모두 균형잡힌 검색 성능
- ✅ HR 전문 용어 검색에 강함
- ✅ 언어 사전과 테이블 정보를 균형있게 처리
- ✅ 다운로드 수 대비 좋아요 비율이 높아 실사용자 만족도 우수
- ✅ 유사도 점수와 실제 검색 정확도가 일치
- ⚠️ 유사도 점수가 다른 모델 대비 상대적으로 낮을 수 있음

**2순위: intfloat/multilingual-e5-large-instruct**

- ✅ 가장 높은 유사도 점수
- ✅ 다중 키워드 처리 우수
- ⚠️ 유사도가 높아도 실제 검색 정확도가 항상 높은 것은 아님
- ⚠️ 모델 내부 벡터화 로직으로 인한 불일치 가능성

**3순위: BAAI/bge-m3**

- ✅ 가장 높은 다운로드 수
- ⚠️ 중국 개발 모델로 중국어 데이터에 편향 가능성
- ⚠️ 유사도 점수가 낮음 (0.6~0.7대)
- ⚠️ 테이블 정보 위주 검색 경향

**기타 모델들**

- **gte-multilingual-base**: 낮은 차원(768)으로 정보 표현력 제한
- **mxbai-embed-large-v1**: 불안정한 검색 결과와 내용 변환 이슈

### 결론 및 권장사항

**최종 선택**: **intfloat/multilingual-e5-large**

**선택 근거**:

1. HR 도메인 특화 테스트에서 가장 일관성있고 정확한 검색 결과 제공
2. 유사도 점수와 실제 검색 정확도의 일치성이 가장 높음
3. 전문 용어, 단일/다중 키워드 등 다양한 검색 시나리오에서 균형잡힌 성능
4. 실사용자 만족도가 높음 (다운로드 대비 좋아요 비율)
5. 언어 사전과 테이블 메타데이터를 균형있게 처리

**향후 고려사항**:

- 현재 테스트 데이터가 multilingual-e5-large로 구축되어 최적화되어 있을 가능성을 고려
- 파인튜닝 수행 시 모든 후보 모델에 대한 재평가 필요
- bge-m3는 유사도는 낮지만 실제 성능이 괜찮아 대안으로 고려 가능
- 다중 키워드 검색 시나리오에서는 -instruct 버전도 검토 가치 있음

## VectorDB 동작

임베딩모델은 텍스트 정보를 벡터 데이터로 변환하는 과정, 즉 전처리 과정을 위한 모델이다. 실제로 데이터를 저장하고 관리를 하기 위해서 실제 VectorDB가 수행하는 프로세스가 중요하다. VectorDB는 임베딩을 통해 생성된 고차원의 벡터 데이터들을 효율적으로 저장하고, 조회할 수 있도록 설계된 데이터베이스입니다. 다만 수천개의 다차원 벡터사이 거리 메트릭을 비교하는 것은 시간이 많이 소요될 수 있기 때문에 VectorDB는 정확도와 속도사이 균형을 유지하는 것이 중요합니다.

이러한 점을 해결하기 위해 VectorDB에서는 아래 그림과 같은 과정을 시행합니다.

### Indexing

인덱싱은 더 빠른 탐색을 가능하게 하는 자료구조로 벡터를 매핑하는 과정입니다. 이 과정에서  여러 `ANNS(Approximate Nearest Neighbors Search)알고리즘`을 활용합니다. 이 알고리즘의 기본 개념은 **정확한 결과보다 타겟과 유사한 값들을 검색하는 것**입니다. 솔직히 인덱싱은 VectorDB에서 가장 중요한 기능이자 핵심이라고 할 수 있습니다.

몇가지 알고리즘을 간단히 소개하고 넘어가겠습니다.

> **References :**
> 
> - [Pinecone/What is a Vector Database?](https://www.pinecone.io/learn/vector-database/)
> - [Pinecone/Nearest Neighbor Indexes for Similarity Search](https://www.pinecone.io/learn/series/faiss/vector-indexes/)
> - [Understanding similarity or semantic search and vector databases](https://medium.com/@sudhiryelikar/understanding-similarity-or-semantic-search-and-vector-databases-5f9a5ba98acb)

#### a. Flat Index (No Optimization)

별도의 Indexing 기법 없이 벡터를 저장하는 방법입니다. 이 과정을 Brute-Force Search, 즉 브루트 포스 검색이라고도 합니다.

저장된 모든 벡터들과 유사도를 계산해 가장 높은 유사도를 지닌 벡터를 찾는 방법으로 검색하는 만큼 단순하고 기본적인 방식이지만, 데이터셋의 크기가 커질수록 계산량이 기하급수적으로 증가하는 명확한 단점이 있습니다.

#### b. Random Projection

랜덤한 벡터를 만들어 원래 벡터와 내적 -> 차원이 줄어들지만 원래 벡터와의 유사성은 유지할 수 있고 고차원의 원래 벡터보다 탐색속도가 빨라질 수 있습니다. 다만 Approximation임을 명심해야 합니다.

> 대체 어떻게 원 벡터와 내적시키면 차원이 줄어드는지 모르는 사람들을 위한 한장요약:  
> ![](https://raw.githubusercontent.com/GRuuuuu/hololy-img-repo/main/2024/2024-05-02-vector-store.md/4.png)
> 
>   
> 3차원상 노란점(1,2,3)을 2차원상의 파란 면에 정사영 시킨다고 했을 때의 예제입니다.

#### c. PQ(Product Quantization)


원 벡터를 균등하게 몇 개의 서브 벡터로 쪼개고, 각 서브 벡터들을 Quantization하여 크기를 줄이는 방법입니다.

![](https://raw.githubusercontent.com/GRuuuuu/hololy-img-repo/main/2024/2024-05-02-vector-store.md/5.png)

빠르고 정확도도 좋으며 큰 데이터셋에서 사용하기 좋은 기법이라고 합니다.

> **Quantization(양자화)란?**  
> 일반적으로 Quantization이란 lower preciision bits로 매핑하는 것을 의미합니다.  
> 예를 들어 우리가 소숫점을 표현할때에는 Float32의 경우, 총 32bit를 사용하고  
> 이를 정수형인 Int8, 총 8bit로 표현한다면 그 경향은 비슷하겠지만 표현할 수 있는 숫자의 범위가 상대적으로 제한될 것입니다.  
> 
> ![](https://raw.githubusercontent.com/GRuuuuu/hololy-img-repo/main/2024/2024-05-02-vector-store.md/6.png)
> 
>   
> 즉, 값을 표현하는데 사용하는 bit수를 줄임으로써 정확도는 다소 떨어지겠으나, 메모리 사용량을 절감시키고, 계산 소요 시간을 줄일수 있다는 장점이 있습니다.

#### d. LSH(Locality-Sensitive Hashing)

![](https://raw.githubusercontent.com/GRuuuuu/hololy-img-repo/main/2024/2024-05-02-vector-store.md/7.png)

벡터들을 Hashing함수에 한번 돌려서 Bucket에 매핑하는 기법입니다.

유사도 검색을 할 때에도 쿼리문에 대한 벡터를 동일한 Hashing함수를 사용하여 **같은 Bucket에 있는 벡터들하고만 비교**하여 찾는 방식으로 동작합니다.

전체 데이터와 비교하는 것이 아니라 Bucket에 있는 데이터들 사이에서만 찾기 때문에 빠르게 검색이 가능합니다.

Bucket이 많을수록 좋은 결과를 낼 테지만, 더 많은 메모리가 필요할 것입니다.

#### e. HNSW(Hierarchical Navigable Small World graph)

이름 그대로, 주어진 벡터들을 가지고 n개의 레이어를 가진 그래프를 생성합니다.  
각 벡터 엣지간 거리는 그 벡터들 사이의 유사도를 나타낸다고 보시면 됩니다.

![](https://raw.githubusercontent.com/GRuuuuu/hololy-img-repo/main/2024/2024-05-02-vector-store.md/8.png)

1. 최상위 레이어의 임의의 노드에서 탐색을 시작하고, 가장 가까운 노드로 이동
2. 현재 레이어에서 더 가까워질 수 없다면 하위 레이어로 이동
3. 모든 벡터가 존재하는 최하위 레이어에 도달할 때까지 반복
4. 쿼리 벡터와 유사도가 가장 높은 벡터 발견!

레이어를 나눔으로써 검색 시 local minimum에 빠지는 것을 방지할 수 있고, 속도와 정확도도 높아 큰 데이터셋에서 쓰기 좋은 기법입니다.

#### f. IVF (Inverted file index)

일반적으로 Inverted Index란 책 맨 뒤에 있는 색인을 생각하시면 됩니다.

![](https://raw.githubusercontent.com/GRuuuuu/hololy-img-repo/main/2024/2024-05-02-vector-store.md/11.png)

맨 처음에는 책의 개요와 목차가 있지만, 책 마지막에는 책에 나왔던 단어들의 리스트와 그 단어가 위치한 페이지를 확인할 수 있는 부분이 있죠!

컴퓨터세상에서는 DB에 데이터를 저장할 때 데이터에서 테이블이나 raw data인 문서의 위치로의 매핑을 같이 저장하는 것을 Inverted Index 혹은 Inverted File이라고 부릅니다.

VectorDB에서의 IVF알고리즘은 **Clustering** + **Inverted File** 이라고 보시면 됩니다.

벡터들을 `K-means` 와 같은 Clustering 알고리즘을 통해 N개의 Cluster로 나누어, vector의 indexd와 각 cluster의 centroid id를 cluster별 **inverted list** 형태로 저장하게 됩니다.

검색 쿼리가 주어지면, 그 쿼리가 포함되는 cluster를 찾고, 해당 cluster의 inverted list 내 벡터들에 대해 검색을 수행하게 됩니다.

그러나 쿼리 벡터가 클러스터에 가장자리에 존재한다면, 아래 사진과 같이 청록색 클러스터의 벡터가 더 가까움에도 불구하고 쿼리벡터가 위치한 빨간색 클러스터의 벡터들에서만 검색을 시도할 것입니다.  

![](https://raw.githubusercontent.com/GRuuuuu/hololy-img-repo/main/2024/2024-05-02-vector-store.md/12.png)

이를 방지하기 위해 `nprobe`라는 파라미터를 도입했고, `nprobe`의 값에 따라 검색할 클러스터의 개수를 지정해줄 수 있습니다.  

![](https://raw.githubusercontent.com/GRuuuuu/hololy-img-repo/main/2024/2024-05-02-vector-store.md/9.png)

  

![](https://raw.githubusercontent.com/GRuuuuu/hololy-img-repo/main/2024/2024-05-02-vector-store.md/10.png)

`LSH`와 `HNSW`알고리즘과 마찬가지로 `IVF`도 검색할 공간을 줄여 검색 속도를 높이는 방법입니다.  
검색할 공간을 줄인다는 의미는, 모든 데이터를 확인하는 것이 아니라 일부만 확인하는 것이므로 검색속도와 정확도를 위해 파라미터 조정이 반드시 필요합니다.

## VectorDB

### 핵심 요구사항

벡터 데이터베이스 선정에 있어 다음 다섯 가지 요구사항이 절대적으로 중요했습니다.

**첫째, on-premise 배포 지원입니다.** 인사 데이터는 직원의 급여, 평가 점수, 개인 정보 등 조직에서 가장 민감한 정보를 포함합니다. 이러한 데이터를 외부 클라우드 서비스로 전송하는 것은 개인정보보호법 위반 가능성이 있을 뿐만 아니라 내부 보안 정책에도 배치됩니다. 따라서 모든 데이터와 처리 과정이 조직 내부 네트워크에서 이루어져야 하며, 외부 API 호출이나 인터넷 연결 없이 완전히 독립적으로 운영 가능해야 합니다.

**둘째, 오픈소스 라이선스입니다.** 시스템의 핵심 인프라로 장기간 사용될 예정입니다. 상용 소프트웨어에 의존할 경우 데이터 규모 증가 시 라이선스 비용이 기하급수적으로 증가할 수 있으며, 벤더가 가격 정책을 변경하거나 서비스를 중단할 경우 대응이 어렵습니다. 오픈소스는 이러한 위험을 제거하고, 소스 코드를 직접 검토하여 보안 감사를 수행할 수 있으며, 필요시 코드를 수정하여 조직의 특수한 요구사항에 맞출 수 있습니다.

**셋째, 복잡한 데이터 구조 지원입니다.** 결과적으로 NL2SQL, 메뉴얼 등 다양한 타입과 계층 구조를 가진 문서, 스키마 정보들을 벡터화하기 위해서 사용할 벡터 데이터베이스는 이러한 복잡한 구조를 벡터화하면서도 원본 정보를 보존하고, 계층 관계를 쿼리할 수 있어야 합니다.

**넷째, 다국어 처리 능력입니다.** HR 분야는 한국어와 영어가 혼용되는 환경입니다. "인사평가"와 "Performance Review"는 같은 의미이지만 다른 언어로 표현되며, 실무에서는 "Performance Review 결과를 제출하세요"와 같이 한영이 섞인 문장도 흔합니다. 벡터 데이터베이스는 이러한 다국어 동의어를 자동으로 인식하고, 한국어 쿼리로 영어 문서를 검색하거나 그 반대도 가능해야 합니다.


이 네 가지 요구사항은 단순한 선호가 아니라 프로젝트 성공을 위한 필수 조건이라고 생각했습니다.

### 주요 제품 분석

시장에는 다양한 벡터 데이터베이스 제품들이 존재하며, 각각 고유한 설계 철학과 장단점을 가지고 있습니다.

#### Pinecone - 클라우드 전용 서비스

Pinecone은 2021년에 출시된 클라우드 전용 벡터 데이터베이스 서비스입니다. "벡터 데이터베이스는 복잡해서는 안 된다"는 철학 아래 설계되어, 개발자가 인프라를 전혀 관리하지 않고 API 호출만으로 벡터 검색 기능을 사용할 수 있습니다.

Pinecone의 가장 큰 장점은 운영 부담이 전혀 없다는 점입니다. 서버 관리, 소프트웨어 업데이트, 백업, 모니터링 등 모든 인프라 관리를 Pinecone이 자동으로 처리하며, 데이터 규모가 증가하면 자동으로 스케일링됩니다. 개발자 경험도 매우 우수하여 5분 이내에 첫 벡터 검색을 구현할 수 있고, 검색 성능도 엔터프라이즈급입니다.

그러나 Pinecone은 바로 on-premise 배포가 불가능하다는 점입니다. 모든 데이터가 Pinecone의 서버로 전송되어 저장되는데, 인사 데이터의 민감성을 고려할 때 이는 받아들일 수 없습니다. 또한 오픈소스가 아닌 상용 소프트웨어로, 데이터 규모 증가 시 비용이 기하급수적으로 증가하며, Pinecone의 독자적인 API에 종속되는 벤더 락인 문제도 있습니다.

#### Chroma - 개발자 친화적 오픈소스

Chroma는 2022년에 출시된 오픈소스 임베딩 데이터베이스로, "개발자가 쉽게 시작할 수 있는 벡터 데이터베이스"를 목표로 합니다. Apache 2.0 라이선스로 완전 무료이며, LangChain, LlamaIndex 등 주요 LLM 프레임워크와 긴밀하게 통합됩니다.

Chroma의 가장 큰 매력은 극도로 낮은 진입 장벽입니다. 별도의 서버 설치 없이 Python 패키지만으로 시작할 수 있으며, 로컬 파일 시스템을 사용하므로 인터넷 연결 없이도 작동합니다. 빠른 프로토타이핑에 이상적이며, 다양한 임베딩 모델을 기본 지원합니다.

그러나 Chroma는 프로덕션 환경에서 사용하기에는 여러 한계가 있습니다. 2022년에 출시된 신생 프로젝트로 대규모 프로덕션 환경에서의 검증이 부족하며, 수백만 개 이상의 벡터나 높은 동시 접속을 처리할 수 있는지 불확실합니다. 엔터프라이즈 기능도 제한적이며, ACID 트랜잭션을 지원하지 않아 데이터 일관성 보장이 약합니다.

결론적으로 Chroma는 PoC(Proof of Concept)나 초기 프로토타이핑 단계에서 빠르게 실험하는 용도로는 적합하지만, 프로덕션 환경에 배포하기에는 검증이 부족합니다. 개발 초기에 Chroma로 실험한 후, 프로덕션 배포 전에 더 안정적인 시스템으로 전환하는 것을 권장합니다.

#### Faiss - Meta의 고성능 검색 라이브러리

Faiss는 Meta(구 Facebook)에서 개발한 고성능 벡터 검색 라이브러리입니다. 2017년에 오픈소스로 공개되었으며 MIT 라이선스를 따릅니다. Faiss는 데이터베이스가 아닌 라이브러리로, 벡터 검색 알고리즘의 최적화된 구현을 제공합니다.

Faiss의 가장 큰 강점은 최고 수준의 성능입니다. C++로 구현되어 극도로 빠르며, Meta 내부 프로덕션 환경에서 수년간 사용되어 안정성이 검증되었습니다. Product Quantization을 통해 메모리 사용량을 획기적으로 줄일 수 있으며, GPU 가속도 지원합니다.

그러나 Faiss는 라이브러리이지 완전한 데이터베이스가 아니라는 근본적인 한계가 있습니다. 메타데이터 관리 기능이 전혀 없어 직원명, 부서, 평가 등급 같은 부가 정보를 함께 저장하고 필터링하는 것이 불가능합니다. 또한 학습 곡선이 가파르고, 프로덕션 환경에서 사용하려면 백업, 모니터링 등 인프라를 직접 구축해야 합니다.

결론적으로 Faiss는 뛰어난 성능을 가진 라이브러리이지만, 단독으로 벡터 데이터베이스로 사용하기에는 부족합니다.

#### Qdrant - 균형잡힌 벡터 검색 엔진

Qdrant는 Rust로 구현된 오픈소스 벡터 검색 엔진으로 2021년에 출시되었습니다. Apache 2.0 라이선스를 따르며, "고성능과 사용 편의성의 균형"을 추구합니다.

Qdrant의 가장 큰 강점은 순수 벡터 데이터베이스로서의 완성도입니다. Rust로 구현되어 메모리 안전성과 성능을 동시에 확보했으며, HNSW 알고리즘을 통해 빠르고 정확한 검색을 제공합니다. "Payload"라는 강력한 메타데이터 시스템으로 복잡한 JSON 구조를 저장하고 필터링할 수 있으며, RESTful API를 제공하여 언어에 구애받지 않고 통합할 수 있습니다.

#### Weaviate - GraphQL 기반 시맨틱 검색

Weaviate는 2019년에 출시된 오픈소스 벡터 데이터베이스로 BSD-3-Clause 라이선스를 따릅니다. "GraphQL 기반의 시맨틱 검색 엔진"이라는 독특한 포지셔닝을 가지고 있습니다.

Weaviate의 특징은 GraphQL API를 제공한다는 점입니다. GraphQL은 RESTful API보다 유연한 쿼리를 가능하게 하며, 하이브리드 검색을 지원하여 벡터 검색과 키워드 검색을 동시에 수행할 수 있습니다. 강력한 스키마 관리 시스템과 자동 벡터화 기능도 제공합니다.


#### PostgreSQL + pgvector - 통합 솔루션

PostgreSQL + pgvector는 기존 PostgreSQL 데이터베이스에 벡터 검색 기능을 추가하는 확장(extension)입니다. pgvector는 2021년에 오픈소스로 공개되었으며 PostgreSQL License를 따릅니다.

pgvector의 핵심 아이디어는 단순하지만 강력합니다. "벡터 데이터를 별도의 전문 데이터베이스에 저장할 필요 없이, 기존 관계형 데이터베이스에서 함께 관리하자"는 것입니다. 새로운 vector 데이터 타입과 인덱스(HNSW, IVFFlat)를 추가하고, 벡터 간 유사도를 계산하는 연산자를 SQL에 추가합니다.

### 종합 평가

**Pinecone**은 운영이 간편하고 성능도 우수하지만, on-premise 배포가 불가능하고 오픈소스가 아니라는 두 가지 필수 요구사항을 충족하지 못해 선택에서 제외되었습니다. 클라우드 전용 서비스로 인사 데이터를 외부로 전송해야 한다는 것은 받아들일 수 없는 조건입니다.

**Chroma**는 오픈소스이고 on-premise 배포가 가능하지만, 프로덕션 환경에서의 검증이 부족합니다. 프로토타이핑 단계에서는 유용하지만 프로덕션 배포에는 적합하지 않습니다.

**Faiss**는 최고의 성능을 자랑하는 라이브러리이지만, 메타데이터 관리 기능이 없고 완전한 데이터베이스가 아니라는 근본적인 한계가 있습니다.

**Qdrant**는 오픈소스이고 on-premise 배포가 가능하며 성능도 우수합니다. 필수 요구사항을 모두 충족하여 최종 후보군에 올랐습니다.

**Weaviate**는 오픈소스이고 on-premise 배포가 가능하지만, GraphQL이라는 기술 스택이 SQL 중심의 개발팀과 맞지 않습니다.

**PostgreSQL + pgvector**는 On-premise 배포가 가능하고, 오픈소스이며, 관계형 데이터와 벡터 데이터를 함께 관리할 수 있어 학습 곡선이 굉장히 낮습니다.

### PostgreSQL vs Qdrant 심층 비교

최종적으로 PostgreSQL + pgvector와 Qdrant 두 제품이 최종 후보로 남았습니다. 두 제품 모두 필수 요구사항을 충족하기에 두 제품을 기준으로 심층적으로 비교를 진행했습니다.

#### **PostgreSQL + pgvector**

**특징**:
- **기존 PostgreSQL에 확장으로 설치** 가능
- **표준 SQL 문법** 사용으로 친숙함
- 벡터 검색과 일반 SQL 연산 결합 가능
- 성숙한 백업, 복제, 고가용성 기능

**장점**:
- 뛰어난 생산성과 유지보수성
- PostgreSQL의 안정성과 확장성을 그대로 활용 가능

**단점**:
- 성능이 Qdrant보다 살짝 떨어지는 경향이 있음
- 규모가 커지면 다루기 어려움

#### **Qdrant**

**특징**:
- **전용 벡터 데이터베이스**로 별도 배포 필요
- **벡터 검색에 특화**된 API 제공
- Docker 기반 컨테이너 친화적 배포
- JSON 기반 DSL로 필터링

**장점**:
- vectorDB 중에 최고 수준의 성능
- 유연한 스케일링

**단점**:
- 조인(Join) 불가능
- 엔터프라이즈 생태계 성숙도 부족
- 트랜잭션 기능 부족
