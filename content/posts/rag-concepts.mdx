> **RAG란?** Retrieval-Augmented Generation의 약자로, 검색과 생성 기술이 결합한 AI 시스템

## RAG의 필요성

기억 기반의 LLM은 학습한 데이터를 바탕으로 텍스트를 생성하지만, 최신 정보나 구체적인 사실을 제공하는 데 한계가 있다. 이를 보완하기 위해 RAG는 필요한 정보를 외부 데이터베이스에서 검색한 후, 이를 기반으로 텍스트를 생성해 정확성과 최신성을 높일 수 있다.

>**기본 동작**
>원본 데이터 -> 적재(load) -> 분할(split) -> 임베딩 -> 벡터 공간 저장(vector store & retriever)

### RAG를 통해 얻을 수 있는 이점

1. **비용 효율적인 구현**
    - 기본적으로 사용하는 LLM를 훈련하기 위해선 컴퓨팅 및 재정적 비용이 많이 소요된다. 하지만 RAG를 통해 LLM에 새로운 데이터를 더 효율적으로 도입할 수 있다.

2. **최신 정보**
    - RAG를 사용해서 LLM을 다양한 정보 그리고 업데이트되는 최신 정보들에 직접 연결해 가져와 임베딩할 수 있다.

3. **사용자 신뢰 강화**
    - RAG는 LLM이 소스의 저작자 표시를 통해 정확한 정보를 제공할 수 있게 할 수 있다. 이 출력 과정에서 소스에 대한 인용 또는 참조가 포함될 수 있다.

4. **개발자 제어 강화**
    - 개발자는 RAG를 사용해 변화하는 요구사항 또는 부서 간 사용에 맞게 LLM의 정보 소스를 제어하고 변경할 수 있다. 또한 개발자는 민감한 정보 검색을 다양한 인증 수준으로 제한하여 LLM이 적절한 응답 생성을 유도할 수 있다.

## RAG의 구성 요소와 작동 방식

### RAG의 주요 구성요소

- **검색 모듈 (Retrieval Module)** : 외부 데이터 소스에서 사용자 질문과 관련된 정보를 검색
- **생성 모듈 (Generation Module)** : 검색 결과를 바탕으로 텍스트를 생성

### RAG의 상세 작동 원리

#### 1. 데이터 전처리 단계

**문서 청킹 (Document Chunking)**
- 긴 문서를 작은 단위로 분할하는 과정
- 일반적으로 200-1000 토큰 단위로 나누며, 문맥이 유지되도록 겹치는 부분(overlap) 설정
- 청킹 전략: 문장 단위, 단락 단위, 의미 단위 등

**벡터 임베딩 (Vector Embedding)**
- 텍스트를 고차원 벡터 공간의 수치로 변환
- 의미적으로 유사한 텍스트는 벡터 공간에서 가까운 위치에 배치
- 주요 임베딩 모델: OpenAI text-embedding-ada-002, Sentence-BERT 등

**벡터 인덱싱 (Vector Indexing)**
- 임베딩된 벡터들을 효율적으로 검색할 수 있도록 인덱스 구조 생성
- 벡터 데이터베이스에 저장 (예: Pinecone, Weaviate, Chroma, FAISS)

#### 2. 검색 단계

**쿼리 임베딩**
- 사용자 질문을 같은 임베딩 모델로 벡터화

**유사도 검색 (Similarity Search)**
- 코사인 유사도, 유클리드 거리 등을 사용하여 가장 관련성 높은 문서 청크 검색
- Top-K 검색: 일반적으로 상위 3-10개의 가장 유사한 청크 선택

#### 3. 생성 단계

**컨텍스트 구성**
- 검색된 관련 문서들을 프롬프트에 포함
- 사용자 질문과 함께 LLM에 입력

**응답 생성**
- LLM이 검색된 컨텍스트를 바탕으로 정확하고 관련성 높은 답변 생성

## 시맨틱 검색과 RAG의 관계

### 시맨틱 검색이란?

시맨틱 검색은 키워드 매칭이 아닌 의미 기반으로 정보를 검색하는 기술로, RAG 시스템의 검색 품질을 크게 향상시킵니다.

### 기존 키워드 검색 vs 시맨틱 검색

- **키워드 검색**: 정확한 단어 일치에 의존, 동의어나 문맥을 이해하지 못함
- **시맨틱 검색**: 의미와 문맥을 이해하여 더 정확한 검색 결과 제공

### RAG에서 시맨틱 검색의 장점

- 방대한 외부 지식 소스에서 더 정확한 정보 검색 가능
- 복잡한 데이터 준비 작업(워드 임베딩, 문서 청킹 등) 자동화
- 관련성에 따른 검색 결과 정렬로 RAG 성능 최적화

## RAG의 한계점과 주의사항

### 주요 한계점

1. **검색 품질 의존성**
    - 잘못된 문서가 검색되면 부정확한 답변 생성
    - 임베딩 모델의 성능에 따라 검색 품질이 크게 좌우됨

2. **컨텍스트 길이 제한**
    - LLM의 토큰 제한으로 인해 제한된 양의 정보만 활용 가능
    - 긴 문서의 경우 중요한 정보가 누락될 수 있음

3. **실시간 정보 업데이트 문제**
    - 벡터 데이터베이스 업데이트에 시간 소요
    - 빈번한 업데이트가 필요한 정보에는 부적합할 수 있음

4. **계산 비용**
    - 임베딩 생성과 벡터 검색에 추가적인 계산 비용 발생
    - 대규모 문서 컬렉션 처리 시 상당한 리소스 필요

### 구현 시 주의사항

1. **청킹 전략**
    - 문서의 특성에 맞는 적절한 청킹 크기와 방법 선택
    - 너무 작으면 문맥 손실, 너무 크면 노이즈 증가

2. **임베딩 모델 선택**
    - 도메인과 언어에 특화된 임베딩 모델 사용 권장
    - 다국어 지원이 필요한 경우 적절한 모델 선택

3. **하이브리드 검색**
    - 시맨틱 검색과 키워드 검색을 결합하여 검색 성능 향상
    - 서로 다른 검색 방식의 장점을 활용

4. **평가 메트릭**
    - 검색 정확도(Precision, Recall)와 생성 품질(BLEU, ROUGE) 모두 고려
    - 도메인별 특화된 평가 기준 설정

### 🔍 AI가 임베딩된 데이터에 없는 내용을 말하는 경우가 있을까?

LLM은 기본적으로 **언어 확률 모델**이기 때문에 "이 문맥에서 다음에 나올 단어가 무엇일까?"를 예측하는 방식으로 동작을 한다.

그래서 프롬프트로 “문서 내용 외에는 답하지 마라”고 해도,  
모델이 _문서의 맥락을 바탕으로 합리적인 추측_ 을 시도하는 경우가 발생하기도 한다.

예를 들어:

> 문서: “FTB Bank는 캄보디아 최초의 상업은행입니다.”  
> 질문: “FTB Bank는 언제 설립되었나요?”
> 
> → 문서에 ‘설립연도’가 없지만, GPT는 “캄보디아 최초 은행이므로 아마 1980년대일 것이다”  
> 같은 답을 시도할 가능성이 있음

---

### 🧠 이런 “추측”을 최소화하려면

#### ✅ 1. **프롬프트 명시적으로 제한**

`You are a strict retrieval QA assistant. You must answer ONLY using the provided context. If the answer is not in the context, say exactly: "해당 정보는 데이터에 없습니다." Do NOT use any prior knowledge or external information.`

이렇게 “단호하게”같은 명확한 금지 문구를 사용하는 걸 지향

---

#### ✅ 2. **temperature = 0**

`temperature=0`으로 설정하면 모델의 창의성이 거의 제거되어, 추측성 문장이 나올 가능성이 낮아진다.

---

#### ✅ 3. **context만 제공**

프롬프트에 **retrieved 문서만 포함**시키고, 시스템/assistant role에도 외부 정보를 주지 않는다. 

예를 들어 LangChain이나 QAChain 설정 시:

```
chain = RetrievalQA.from_chain_type(     
	llm=ChatOpenAI(model="gpt-4o-mini", temperature=0),     
	retriever=retriever,     
	chain_type_kwargs={         
		"prompt": qa_prompt  # context 기반으로만 대답하게 설계     
	} 
)
```

---

#### ✅ 4. **응답 필터링**

모델이 혹시라도 외부 지식을 언급할 경우를 대비해,  
“context 외부 정보 탐지 필터”를 넣어 추측성 대답을 안하게 만들 수 도 있다.

예:
- 응답에 `"제 생각에는"`, `"보통은"`, `"일반적으로"` 같은 문장이 있으면 재질문 or 차단
- “데이터에 없습니다” 패턴만 허용

---

#### ✅ 5. **RAG 모델에 guard LLM 추가**

 LangChain에서 “2단계 검증 구조” 로 질문을 검증을 할 수 있다.
1. **GPT A:** 문서 기반 답변 생성
2. **GPT B:** “이 답변이 context 안의 정보로부터만 만들어졌는가?” 검증    

LangChain에서는 이를 “**RetrievalQAWithVerificationChain**” 형태로 구현할 수 있다.

—

### ✅ 결론

> 완전히 0은 아니지만,  
> **프롬프트 설계 + temperature=0 + context 제한**으로  
> 실질적으로 “문서 외 추측 없음” 수준까지 만들 수 있습니다.
