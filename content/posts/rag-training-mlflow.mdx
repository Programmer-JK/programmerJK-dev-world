## 1. 조사 목적

본 보고서는 도메인 특화 검색 및 질의응답(RAG) 시스템의 성능 개선을 위해 고려 중인 **모델 학습 전략**과, 이를 **MLflow 기반 실험 관리 체계로 운영할 수 있는지 여부**를 종합적으로 검토하기 위해 작성되었다.

특히 다음 질문에 대한 실무적 판단을 목표로 한다.

- 현재 성능 저하 문제를 **학습으로 해결해야 하는 시점인가**
- 어떤 모델 유형부터 학습하는 것이 **ROI 측면에서 합리적인가**
- 임베딩, 리랭커, LLM 파인튜닝을 **MLflow로 일관되게 관리할 수 있는가**

---

## 2. 모델 후보군 개요

### 2.1 임베딩 모델

|구분|모델|특징|
|---|---|---|
|현재 사용|intfloat/multilingual-e5-large|다국어 지원, 범용 성능 안정|
|대안 1|BAAI/bge-m3|다국어 + 코드스위칭 강점, 장문 문서 적합|
|대안 2|intfloat/multilingual-e5-large-instruct|지시형 쿼리 이해 우수|

임베딩 모델은 검색 품질에 가장 큰 영향을 미치며, 비용 대비 성능 개선 효과가 높아 **학습 우선순위 1순위**로 분류된다.

---

### 2.2 크로스-인코더 (리랭커)

|모델|특징|활용 포인트|
|---|---|---|
|ms-marco-MiniLM-L6-v2|경량, 빠른 학습|기본 리랭킹|
|ms-marco-TinyBERT-L2-v2|초경량|리소스 극소 환경|
|ms-marco-MiniLM-L12-v2|고성능|정확도 최우선|

크로스-인코더는 Top-k 문서 정렬 품질을 크게 개선하며, **짧은 학습 시간 대비 정확도 상승폭이 큰 영역**이다.

---

### 2.3 LLM 모델

#### 경량 LLM

- Qwen/Qwen3-8B
- Qwen/Qwen2.5-7B-Instruct
- Meta-Llama-3-8B-Instruct

#### 메인 LLM

- Qwen3-32B
- Qwen3-30B-A3B

LLM은 응답 품질과 톤앤매너에 영향을 주지만, 학습 비용과 리스크가 크기 때문에 **검색/랭킹 모델 이후 단계**로 고려한다.

## 3. 학습 필요 시점 판단 기준

학습 필요성은 검색 정확도 및 서비스 단계에 따라 다음과 같이 구분된다.

### 3.1 즉시 학습 필요 (High Priority)

- 도메인 특화 검색 정확도 < 60%
- 전문 용어, 약어 인식 실패 다수
- 한영 코드스위칭 문서/쿼리 다량 존재

→ vectorDB 수정 및 임베딩 체크 이후 임베딩 및 크로스-인코더 학습 우선

---

### 3.2 선택적 학습 (Medium Priority)

- 쿼리 변환 품질 개선 필요
- 특정 포맷의 메타데이터 추출 요구
- 브랜드 톤앤매너 중요

→ 프롬프트 수정 및 파이프라인 수정 이후 경량 또는 메인 LLM 파인튜닝 검토

---

### 3.3 학습 불필요 (Low Priority)

- 범용 질의응답
- 문서 수 < 10,000
- PoC / 프로토타입 단계

→ API 기반 모델 활용 권장

## 5. 학습 방법론

### 5.1 임베딩 파인튜닝

- 방식: Contrastive Learning
- 목적: 도메인 용어, 코드스위칭 인식 개선
- 데이터 설계가 80%
- 파라미터 튜닝은 거의 의미 없음
- MLflow로 epoch 단위 지표 관리

### 5.2 크로스-인코더 파인튜닝

- 데이터: (쿼리, 문서, 관련도 점수)
- 손실 함수: Cross-Entropy Loss (쌍별 비교)
- 기대 효과:
    - Top-3 정확도: +20%p
    - 거짓양성 비율: -66%
- 소량 데이터 + 빠른 실험  
- 가장 ROI가 높은 학습
- 짧은 피드백 루프

### 5.3 LLM 파인튜닝

- 방식: LoRA / PEFT
- 목적: 쿼리 변환, 응답 포맷, 톤 조정
- Instruction 품질이 전부
- 자동 지표만으로는 불충분
- Human Eval 필수

## 6. MLflow 적용 가능성 분석

### 6.1 MLflow로 관리 가능한 영역

#### 임베딩 / 리랭커

- Params: 모델, 하이퍼파라미터
- Metrics: MRR@10, Recall@5, nDCG@10
- Artifacts: 모델 체크포인트, 평가 리포트

→ MLflow와 **완벽히 적합**

---

#### LLM 파인튜닝

- Loss, PPL 등 학습 지표 추적 가능
- Human Evaluation 결과는 artifact로 관리

→ MLflow는 **실험 기록 및 버전 관리 용도**로 적합

---

### 6.2 MLflow 활용 시 권장 역할 정의

**MLflow가 강력한 영역**:
- 검색/랭킹 모델: 자동 지표 (MRR, Recall) 추적
- 하이퍼파라미터 비교 실험
- 모델 버전 관리 및 롤백

**MLflow 한계**:
- LLM 응답 품질은 수치화 어려움
- Human Eval 워크플로우 부족
- A/B 테스트 통합 제한적

**보완 방안**:
- LLM: MLflow (학습 기록) + 별도 Human Eval 시스템
- 또는 LangSmith, Braintrust 같은 LLM 전용 도구 병행

---

## 7. 기대 효과

### 7.1 검색 성능 개선

- MRR@10: 0.65 → 0.80~0.85
- Recall@5: 0.72 → 0.88~0.92

### 7.2 응답 품질

- 정답 포함률: 70% → 85%+
- 환각 빈도: 30% → 15~20%

### 7.3 운영 효율

- 평균 검색 문서 수: 10개 → 5~7개
- 토큰 비용: 30~50% 절감

---

## 8. 제약사항 및 리스크

### Critical

- 데이터 품질 (오레이블 10% 시 성능 급락)
- **인력 (필수)**: 
	- ML 엔지니어 1명 (풀타임) 
	- 데이터 레이블러 1-2명 (파트타임 또는 외주) 
	- 도메인 전문가 (데이터 검수, 주 4-8시간)

### Important

- 과적합 위험 → 데이터 증강 필요
- 도메인 이동 → 3~6개월 재학습 필요

### Compliance

- 개인정보 및 저작권 이슈
- 연간 운영 비용 $20K~50K

## 10. 결론 및 권고 사항

- 현재 상황에서는 **임베딩 + 크로스-인코더 학습이 가장 높은 ROI**를 제공
- 제안된 학습 전략은 **MLflow 기반으로 충분히 운영 가능**
- LLM 학습은 검색 정확도 개선 이후 단계로 제한적으로 진행 권장

본 조사 결과를 바탕으로, 단계적 학습 및 MLflow 실험 관리 체계 도입을 추진하는 것이 합리적인 선택으로 판단된다.
