## 결과 한눈에

- 마이그레이션 데이터 전체 용량 **5GB → 약 1/10**
- 레코드당 크기 **100MB → 10MB**, 렌더링 **10배 이상** 빨라짐

## 문제 해결 사례

### 1. 위키 → Oracle 대용량 마이그레이션

기존 위키(Confluence)에 쌓인 영업점 방문 기록을 새 시스템으로 옮겼다. 위키 HTML을 태그 단위로 잘라 임시 테이블에 올리고, 첨부 이미지는 base64로 바꿔 넣는 Java 도구를 만들었다. 적재 중 장애가 세 단계로 나타났다 — 테이블스페이스 부족, 서버 OOM, 그리고 DB 서버 다운. 이 과정은 [유적 기록](/posts/orgn-migration-postmortem)에 따로 정리했다.

현업 담당자가 직접 돌릴 수 있도록 마이그레이션을 **버튼 한 번 + 실시간 진행률·로그** 웹 화면으로 만들었다.

### 2. 폐쇄망에서 Notion식 에디터

표와 이미지를 자유롭게 넣고 슬래시 명령을 쓰는 에디터가 필요했다. 처음엔 editor.js로 새로 만들 계획이었지만, 반입 리스크를 줄이려고 **이미 이식된 Summernote에 플러그인을 붙이는 쪽**으로 바꿨다. 이미지 크기 편집을 위해 0.9.1로 올리고 크기 조절, 확대 보기, 조회 모드 툴바 숨김까지 구현했다. 가장 오래 붙잡은 문제는 [플러그인 로딩](/posts/summernote-plugin-loading-iframe)이었다.

### 3. 보안 정책에 따른 지도 전환

지점과 직원 위치를 보여주던 지도검색 화면이 보안 이슈로 기존 지도 API를 쓸 수 없게 됐다. IBMap으로 교체해 마커와 이동시간 경로선을 다시 구현했고, 개발 → 반입 → 라이선스 → 개발서버 → 운영 배포까지 직접 조율했다. 기존 좌표를 위경도로 바꾸는 [좌표 변환 함수](/posts/oracle-wcongnamul-to-wgs84)도 이때 만들었다.

## 반복해서 쓴 접근법

1. **원인을 층마다 분리한다** — 마이그레이션 장애를 공간 → 레코드 크기 → 임시 LOB 순으로 하나씩 걷어냈다.
2. **환경 제약 안에서 대안을 고른다** — 반입 부담 때문에 기존 에디터를 확장했고, 보안 정책에 맞춰 지도를 바꿨다.
3. **운영자가 혼자 쓸 수 있게 만든다** — 원클릭 실행 화면과 실시간 로그, 안내 문구의 설정값 분리.
