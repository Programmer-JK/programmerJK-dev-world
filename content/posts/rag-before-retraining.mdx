# 재학습 이전 적용 사항 (RAG 운영 필수 가이드)

> 이 문서는 **읽고 이해하는 문서가 아니라, 그대로 따라 하면 되는 운영 플레이북**다.
> 
> 질문 하나에 대해 아래 3가지만 바로 답할 수 있게 만드는 것이 목적이다.
> 
> 1. 지금 문제는 **어느 레이어**인가?
>     
> 2. **재학습 전**에 내가 반드시 해봐야 할 조치는 무엇인가?
>     
> 3. **지금 당장 할 액션**은 무엇인가?
>     

---

## 0. 이 문서를 쓰는 방법 (가장 중요)

### 📌 상황 가정

- “요즘 RAG 답변이 이상하다”는 이슈가 올라옴
    
- On-call / 운영자가 **10분 안에 판단**해야 함
    

### 📌 이 문서를 쓰는 순서

```
① Eval 데이터 동일한지 확인
② Recall@K 하나만 본다
③ MRR 하나만 본다
④ Answer 지표는 샘플로만 본다
⑤ 여기까지 다 했는데도 안 되면 → 그때만 재학습 논의
```

👉 **위 순서를 어기면 이 문서는 의미가 없다**

## 1. 이 문서의 사용 대상

- RAG 서비스 운영자 (On-call)
    
- 검색 / 랭킹 / LLM 파이프라인 담당자
    
- “재학습 할까요?”라는 질문에 답해야 하는 Tech Lead
    

---

## 2. 가장 중요한 전제

### 2.1 "Document"는 물리적 파일이 아니라 **의미 단위**다

운영에서 가장 많이 헷갈리는 부분이 여기다.

> ❌ Document = PDF 1개 / 파일 1개  
> ✔ Document = **사용자가 질문에 답을 얻는 데 필요한 의미 단위**

따라서 아래는 모두 허용된다:

|상황|Document 정의 예|
|---|---|
|PDF 1개, 구조 명확|PDF 1개 = Document 1개|
|PDF 1개, section 분리 어려움|PDF 전체 = Document 1개|
|여러 파일에 답이 분산|파일 여러 개 = Document 여러 개|
|위키/HTML|페이지 단위 또는 주제 단위|

👉 **Document 개수는 1개일 수도, N개일 수도 있다**

---

### 2.2 Chunk는 "쪼갠 조각"일 뿐, 정답 단위가 아니다

- Chunk는 검색/랭킹을 위한 기술적 단위
    
- PDF에서 section을 못 나눠도 **chunk는 자동 생성 가능**
    
- Chunk 전략은 언제든 바뀔 수 있다
    

👉 그래서:

- Recall은 **Document 기준**
    
- MRR은 **Chunk 기준 (1:N)**
    

이 분리를 하지 않으면 평가가 무너진다

---

## 3. 지표를 이렇게 나눠서 본다 (역할 분리)

```
[Retrieval]  "찾았는가?"
 ├─ Recall@K (문서 기준)
 └─ Hit@K

[Ranking]    "잘 올렸는가?"
 └─ MRR (chunk 기준, 1:N)

[Answer]     "잘 말했는가?"
 ├─ Accuracy
 └─ Faithfulness

[System]     "운영이 망가졌는가?"
 └─ Fallback / Latency
```

👉 **지표 하나 = 질문 하나**라고 생각하면 된다

---

## 4. Eval 데이터는 이렇게 생겼다 (왜 이 구조인가)

```json
{
  "query_id": "q_001",
  "query": "환불은 언제까지 가능한가?",
  "gold": {
    "doc_ids": ["D1"],
    "chunk_ids": ["D1_C2", "D1_C3"]
  }
}
```

### 이렇게 나눈 이유

|항목|의미|누가 만드나|
|---|---|---|
|doc_ids|이 질문의 **정답 문서**|사람 (안 바뀌어야 함)|
|chunk_ids|답이 들어있는 **후보 chunk들**|시스템 (chunk 전략 따라 자동)|

👉 **사람이 chunk_id를 전부 관리하려고 하면 운영 불가능**

---

## 5. Step 1 — Retrieval 먼저 본다 (가장 중요)

### 5.1 Recall@K 하나만 보면 된다

**질문**

> “정답 문서를 **찾기라도 했는가?**”

**기준 (K=10 예시)**

|Recall@10|해석|지금 할 일|
|---|---|---|
|≥ 0.85|잘 찾음|다음 단계로|
|0.80~0.85|애매|Top-K / Chunk 조정|
|< 0.80|못 찾음|다른 건 보지 말고 Retrieval부터 고쳐라|

👉 Recall이 낮은데 MRR, Prompt 보면 **100% 헛수고**

---

## 6. Step 2 — Ranking은 그 다음이다

### 6.1 MRR은 이렇게 해석한다

**질문**

> “찾은 문서 중에서, **정답 chunk를 위로 올렸는가?**”

**운영 기준**

|조건|해석|지금 할 일|
|---|---|---|
|Recall 정상 & MRR ≥ 0.35|정상|유지|
|Recall 정상 & MRR < 0.35|랭킹 문제|Re-ranker Top-N ↑|
|Recall도 낮음|랭킹 볼 필요 없음|Retrieval로 복귀|

👉 MRR은 **Recall이 정상일 때만 의미가 있다**

---

## 7. Step 3 — Answer 지표는 "샘플"만 본다

### 7.1 Accuracy

- 주 1회
    
- 30~50개
    
- 실패 / 재질문 위주
    

|Accuracy|해석|할 일|
|---|---|---|
|≥ 0.75|괜찮음|유지|
|0.65~0.75|불안|Prompt 수정|
|< 0.65|심각|Prompt/Context 재설계|

### 7.2 Faithfulness

> “이 답변, **근거 문서에 써 있는 말인가?**”

|Faithfulness|해석|할 일|
|---|---|---|
|≥ 0.90|정상|유지|
|0.80~0.90|위험|Grounding Prompt 강화|
|< 0.80|사고|Context 줄이고 Prompt 고쳐라|

---

## 8. Step 4 — 시스템 지표는 경보용이다

### Fallback Rate

|Fallback|의미|할 일|
|---|---|---|
|≤ 10%|정상|무시|
|10~15%|이상|Routing 점검|
|> 15%|장애|Intent 규칙 수정|

---

## 9. 재학습은 언제 꺼내는가 (이게 핵심)

아래 **모두 Yes**일 때만 재학습 얘기를 한다:

-  Recall 조정 다 해봤다
    
-  Re-ranker 조정 다 해봤다
    
-  Prompt / Context 다 만져봤다
    
-  그래도 **같은 문서로 같은 질문이 계속 틀린다**
    

👉 이 조건 아니면 **재학습 논의 금지**

---

## 10. 재학습 이전 적용 사항 요약 (이 문서의 핵심)

이 문서의 목적은 **"지표를 어떻게 보느냐"가 아니라**

> **"재학습을 논의하기 전에, 운영에서 무엇을 반드시 적용했는가"를 정의하는 것**이다.

아래 항목은 **재학습 검토 전에 반드시 적용·검증되어야 하며**,  
하나라도 빠지면 재학습 논의는 중단한다.

---

### A. Retrieval 레이어 (Embedding 재학습 이전)

반드시 적용:

-  Recall@10 또는 Recall@20 측정 (Document 기준)
    
-  Top-K 확장 (최소 10 → 20)
    
-  Chunk overlap ≥ 10%
    
-  Hybrid Search (Dense + BM25) ON
    

재학습 논의 가능 조건:

```text
- Recall@20 < 0.80
- 위 조치 적용 후에도 개선 없음
```

---

### B. Ranking 레이어 (Re-ranker 재학습 이전)

반드시 적용:

-  Recall 기준선 충족 여부 확인
    
-  Re-ranker Top-N ≥ 20
    
-  Threshold 완화 또는 제거
    
-  Re-ranker ON/OFF 비교 실험
    

재학습 논의 가능 조건:

```text
- Recall 정상 (≥ 0.85)
- MRR < 0.35
- Ranking 조정으로 개선 없음
```

---

### C. Answer 레이어 (vLLM / sLLM 재학습 이전)

반드시 적용:

-  Grounding Prompt 적용
    
-  Context 상위 3~5개로 제한
    
-  출처 기반 Context 구조화
    
-  Prompt 수정 이력 및 실패 사례 로그 확보
    

재학습 논의 가능 조건:

```
- Retrieval / Ranking 정상
- Accuracy 또는 Faithfulness 기준선 미달
- 동일 질문 반복 실패
```

---

## 11. vLLM / sLLM Fine-tuning 적용 가이드 (재학습 단계)

> Fine-tuning은 성능 개선 수단이 아니라 **운영 규칙을 모델에 고정**하기 위한 단계다.  
> Prompt / Context 조정으로 해결 가능한 문제에는 적용하지 않는다.

### 11.1 Fine-tuning 검토 트리거

다음 중 하나라도 명확히 해당하면 Fine-tuning 검토 가능:

- 전문 용어, 내부 약어, 도메인 표현을 반복적으로 오인식
    
- NL2API / NL2SQL에서 Intent는 맞으나 포맷·파라미터 오류가 반복 발생
    
- 동일 질문 + 동일 문서 + 동일 Prompt 조건에서 답변이 계속 흔들림
    

---

### 11.2 Fine-tuning 방법 분류

#### A. Instruction Fine-tuning (권장)

- 목적: 답변 규칙, 표현, 포맷을 고정
    
- 데이터: Instruction / Input / Output 형태
    
- 특징:
    
    - 소량 데이터로 효과적
        
    - 기존 능력 훼손 위험 낮음
        

적합한 경우:

- 답변 톤 불안정
    
- 규칙 설명 방식 통일 필요
    
- 기본 NL2API 포맷 고정
    

---

#### B. Supervised Fine-tuning (SFT)

- 목적: 특정 질문에 대한 정답을 직접 학습
    
- 데이터: Question / Answer 쌍
    
- 특징:
    
    - 효과는 확실하나 범용성 감소 위험
        

적합한 경우:

- FAQ
    
- 정책 / 규정 Q&A
    
- 내부 매뉴얼 응답
    

---

#### C. Format / Function Fine-tuning (NL2API / NL2SQL)

- 목적: 자연어 → 구조화 결과(JSON, SQL 등) 안정화
    
- 데이터: 자연어 입력 → 구조화 출력
    
- 특징:
    
    - 포맷 안정성 대폭 향상
        
    - Prompt 대비 비용 및 설계 난이도 높음
        

적합한 경우:

- NL2API
    
- NL2SQL
    
- Workflow 트리거 모델
    

---

### 11.3 적용 비권장 방식

- Reinforcement / Preference 기반 학습 (RLHF, DPO 등)
    

사유:

- 비용 대비 효과 불명확
    
- 재현성 및 디버깅 어려움
    
- 운영 환경에서 원인 분석 불가
    

---

### 11.4 vLLM / sLLM 재학습 핵심 원칙

- Prompt로 해결 가능하면 재학습 금지
    
- 재학습은 "정답을 가르치는 것"이 아니라 "운영 규칙 고정"
    
- 재학습 전후 지표 변화는 반드시 로그로 비교

```
## 핵심 원칙 (제목에 대한 최종 답)

> **재학습은 개선 수단이 아니라,**  
> **정의된 운영 적용 사항을 모두 통과했을 때만 열리는 최후의 선택지다.**

```
