처음엔 체인으로 충분해 보였다. 질문을 받고, 검색하고, 답한다. 그런데 "검색 결과가 부족하면 다시 찾는다", "실행 전에 사람이 확인한다" 같은 요구가 붙는 순간 일직선 파이프라인은 if 문으로 뒤덮이기 시작했다.

## 왜 체인이 아니라 그래프였나

체인은 흐름이 한 방향일 때 가장 읽기 쉽다. 하지만 에이전트의 실제 흐름은 되돌아가고, 갈라지고, 멈춘다. LangGraph를 고른 이유는 기능보다 표현력이었다. 노드와 엣지로 그려 두면 코드가 곧 흐름도가 된다.

## State를 먼저 설계한다

모든 노드는 State를 읽고 일부를 갱신해서 돌려준다. 그래서 State의 모양이 곧 노드 사이의 계약이 된다.

```python
from typing import TypedDict, Annotated
import operator

class AgentState(TypedDict):
    question: str
    results: Annotated[list[str], operator.add]
    retries: int
```

## 노드는 작게, 엣지는 명확하게

판단의 결과로 어디로 갈지는 노드가 아니라 조건부 엣지가 결정한다. 재시도 루프는 반드시 탈출 조건을 State에 두고, 결국 상태 머신을 명시적으로 그리는 일이 된다.

```python
graph.add_conditional_edges(
    "reviewer",
    route_after_review,
    {"retry": "executor", "done": END},
)
```
